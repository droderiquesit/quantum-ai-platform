## 4. What is true today

**What runs as a process.** Nothing runs continuously outside a test. In the
`algorik-dev` GCP project, environment `dev`, five Cloud Run services have
been observed answering real HTTP requests as of 2026-09-04: the portal and
landing (public, `200`, correct titles), OpenObserve (public per ADR 0030,
`200`/`401` as designed), and `qip-dev-api`/`qip-dev-fastbrain`/
`qip-dev-deepbrain` exist behind internal ingress (Google Frontend `404`,
which is the shape of "a service exists here," not "no service exists").
`qip-dev-fastbrain` is separately confirmed, from a CI run's own output, to
be serving the attested image built and signed by this branch's pipeline.
None of the five has had its running revision's digest, secret mounts, or
service identity independently confirmed by an authenticated read from
outside the project — every claim above rests on an unauthenticated `GET` or
on CI's own self-report. No execution node exists in any environment
(`execution_nodes = {}` in dev, test, stage and prod —
`grep -rn execution_nodes infrastructure/environments/*/terraform.tfvars`).

**The node is unbuildable, not unauthorised, and the distinction was
corrected at `bcf7330`.** ADR 0035 authorises exactly one — `newyork-1`,
`us-east4`, shadow mode, dev only — and the authorisation is real. Three
files used to say the blocker was that no venue's published address ranges
had been recorded; ADR 0035 supersedes that, because the node prices from
`QIP_VENUE_FEED=simulated`, the in-process matching engine, and needs no
venue ranges at all. An agent reading the old text would conclude the node
was unauthorised when it is authorised. What actually blocks it is two values
a person supplies and Terraform cannot derive: **no boot image exists**, and
**`region_allocation` is a capital ceiling only the owner may choose**. The
first of those changed shape at `5ccaea9` and the old half-sentence — "and
nothing in this repository builds one" — is **withdrawn**: `5ccaea9` added
`.github/workflows/image.yml`, `infrastructure/images/execution-node/` and
`infrastructure/terraform/modules/image-bake/`, which build a Compute Engine
image from the container image `deploy.yml` already attested. **A bake now
exists and no image does, and both halves matter.** The workflow has never
been dispatched: `GET /repos/…/actions/workflows/image.yml/runs` answers
`total_count: 0`, against a workflow GitHub registered at
`2026-09-06T08:14:25Z` and reports `active`. **Check the run count, not the
workflow's existence** — earlier the same day the endpoint answered `404`
because GitHub had not yet seen the file, and a reader who wrote that down
would now find a `200` and mistake registration for a run — and
`image_bake_subnet_cidr` is commented out in
`environments/dev/terraform.tfvars:203`, so `module.image_bake` has
`count = 0` (`terraform/main.tf:631`) and creates nothing. `boot_image` has no
value in any environment: every occurrence in a tfvars file is inside a
comment. So the value a person writes into `execution_nodes` still does not
exist; what changed is that producing one is now three human acts named in the
tfvars header rather than a build step nobody has written. Both were left
unsupplied rather than invented — a plausible self-link would have produced a
plan that reads as ready and an apply that fails after a subnet, an identity
and four IAM bindings exist. A `boot_image` validation added at `bcf7330`
(`modules/execution-node/variables.tf:104-146`) now requires a full image
self-link and was proven in both directions against the real module:
`debian-12` and an image family refused, both legal self-link spellings
admitted — the second half being what separates a gate from a refusal of
everything. So `execution_nodes = {}` is a working configuration, not an
incomplete one.
