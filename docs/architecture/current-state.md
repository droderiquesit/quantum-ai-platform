## The fact that governs everything below

**No process of this platform is running in any environment today.** `execution_nodes = {}`
in every environment, so the edge cell's hot path runs only under `cargo test`. The three
Cloud Run binaries are built and attested but have no live service: the GitOps control
plane that reconciles them is suspended (ADR 0093), and the dev project's billing is
disabled, so `deploy.yml` fails at image push. A capability below that is "reached from
production" is reached from a *composition root*, not from a running process.

**312 component records** in 14 groups. Reached from a composition root: yes 171, partial 53, n/a 45, tests-only 38, broken 3, no 1, unknown 1.


## apps

Six Rust binaries (qip-api, qip-fastbrain, qip-deepbrain, qip-edge-node, qip-cli) plus one library-only "app" (qip-web, no main.rs) implement nearly the full blueprint surface: API/console/mesh/treasury (qip-api, 262 tests), fast execution (qip-fastbrain, 98 tests), research/evolution/learning (qip-deepbrain, 169 tests), the regional edge cell (qip-edge-node, 129 tests), an operator CLI (qip-cli, 34 tests) and no-JS server-rendered pages (qip-web, 37 tests). qip-api, qip-fastbrain and qip-deepbrain are built, attested and digest-pinned for Cloud Run but currently have no live service anywhere: dev was observed serving 2026-09-04, torn down 2026-09-13, and a 2026-09-20 reapply could not restore service because deployment moved (ADR 0036) to a GitOps/Argo CD control plane that ADR 0093 has since suspended. qip-edge-node is fully implemented and image-built but has never run outside tests in this repository's history because every environment sets execution_nodes = {}. qip-cli is deliberately never containerized (an operator tool by design, per deploy.yml).

Notable gaps:

- qip-edge-node: never deployed in any environment (execution_nodes = {} in dev/test/stage/prod terraform.tfvars); ADR 0035 authorises exactly one shadow-mode node but its boot image has never been baked and its capital allocation has never been chosen by an operator.
- qip-api, qip-fastbrain, qip-deepbrain: built and previously observed serving on Cloud Run in dev (2026-09-04), torn down 2026-09-13, and currently unreachable because the GitOps control-plane cluster that would reconcile their RunService manifests is suspended (ADR 0093) — deployment is blocked on infrastructure/CI state, not on missing application code.
- qip-api's mesh backbone (mesh.rs) and qip-deepbrain's source-discovery/connector arms are structurally complete and tested but have no wired configuration in any environment, so they run only in tests today.
- qip-api GET /data-sources always answers a fixed 'unavailable' body by design; the ledger/capital-call write surfaces exist but explicitly settle, post or fund nothing in this build.
- qip-fastbrain: every configured feed (synthetic, replay, connector) is explicitly marked not production-grade in its own tests; no capital decision may rest on it as shipped.
- qip-deepbrain: QIP_CENTRAL_HORIZONS_PATH is read by the composition root but wired in no environment, so the §23.4 horizon gate never arms in any deployment.

## delivery

This is the CI/CD, tooling and governance-register layer: 5 GitHub Actions workflows (ci/deploy/image/infra/vendor), 15 scripts (dependency/secret/manifest/provider gates, a delivery-register auditor, deploy/bootstrap tooling, and dev-only browser-automation/LLM-gateway tools explicitly walled off from backend/frontend), the Makefile (14 targets mirroring ci.yml 1:1), the .claude/ harness config (13 agents, 8 skills, 2 hooks + their test runner, the rules tree, settings.json), all 32 qip-acceptance cross-cutting test suites (317 #[test] functions total), and the two governance documents (docs/adr/README.md indexing 98 ADRs, docs/DELIVERY-STATUS.md scoring all 181 blueprint sections). ci.yml, the dependency/secret/manifest/provider check scripts, and the Makefile are all actively exercised and mutually consistent; infra.yml and vendor.yml are structurally sound but currently blocked end-to-end because Argo CD's own container image fails the platform's Trivy CVE gate with no upstream fix available, so the GitOps control plane has never successfully bootstrapped in any environment. docs/DELIVERY-STATUS.md's own latest headline tally: REACHED 46 (25%), PARTIAL 119 (66%), UNREACHED 1 (1%), ABSENT 0, NARRATIVE 15 (8%) of 181 sections — and its single governing fact is "Nothing is deployed. No process of this platform has ever been observed running."

Notable gaps:

- The GitOps control plane (infra.yml action=up, gitops.rs's whole subject) has never successfully bootstrapped anywhere: run 52 applied 238 Terraform resources cleanly but failed at the bootstrap step because vendor.yml's blocking Trivy gate refuses Argo CD's image on CVE-2025-68121 (no fixed upstream kustomize/git-lfs exists), which also blocks cert-manager's images in the same fail-fast loop — dev is now suspended (ADR 0093).
- Makefile's `test` target (Makefile:54-55) omits --no-fail-fast, unlike ci.yml's test job, the Makefile's own `count` target, and top-level CLAUDE.md's documented command — a local `make test` can abort at the first failing binary and under-report, the exact failure mode the file's own comment warns against.
- docs/adr/README.md claims ADR number 0097 (unlinked placeholder row, 'body to follow') but no 0097 file exists anywhere in docs/adr/ — a genuinely unwritten claimed ADR; separately, ADR 0099's body already exists on disk (185 lines, untracked) but the README still shows it as an unlinked placeholder, so the index lags the working tree.
- .claude/rules/01-security-and-safety.md still names the destructive-command guard hook 'guard-dangerous-command.sh'; the actual, current implementation is guard-dangerous-command.py (a documented rewrite motivated by a shell-quoting bug) — the rules doc was not updated for the language change.
- deploy.yml's final step ('replace every execution node under its group's rolling policy') is a structural no-op today: every environment's Terraform tfvars sets execution_nodes = {}, and image.yml (which bakes the boot image that step would deploy) has never been dispatched.
- Three delivery-tooling scripts (audit-dead-code.py, audit-register.py, and the venue-signup/model-gateway dev tools) were not found wired into ci.yml or the Makefile during this pass — they appear to be manually/agent-invoked rather than gated, worth confirming separately.
- docs/DELIVERY-STATUS.md explicitly refuses to compute a single delivered-percentage headline because the 181 blueprint sections are not equal-weight units (one bundles 9 execution domains, another is an 18-row control table) — 'PARTIAL at 66%' is stated as the accurate shape of the platform, not a hedge, and the document instructs readers to track individual rows rather than the aggregate.

## edge-cell

qip-edge is a 19,968-line (37,655 with tests) crate implementing the whole regional edge-cell hot path (ADR 0008) as one `Cell` aggregate in src/cell.rs (9,040 lines): feed ingestion, feasibility, pricing/netting/crossing, arbitrage-cycle decomposition and passive-first dispatch, region capital reservation, settlement-timing checks, mesh state-up/capital-down, a hash-chained journal, and Prometheus-shaped telemetry. It is exhaustively tested (315 #[test] functions across 20 src modules and 26 integration files) and is called from a deployable binary's non-test code (qip-edge-node and qip-cli's demo subcommand), but qip-edge-node itself is instantiated in zero Terraform environments (execution_nodes = {} everywhere), so no live process runs this hot path today.

Notable gaps:

- qip-edge-node (the only binary that runs Cell::work) is deployed in no environment: execution_nodes = {} in infrastructure/environments/{dev,test,stage,prod}/terraform.tfvars, so the crate's whole hot path, and everything it would emit to Prometheus via CellMetrics, reaches no live process.
- qip-api declares qip-edge only under [dev-dependencies] (Cargo.toml:50) and every qip_edge:: mention in qip-api/src is a doc comment, not real code -- the serving binary never actually touches this crate.
- The crate's Cargo.toml pins qip-execution-engine as a dependency that zero src files import; its own comment says it exists only to satisfy an architecture test's 'vacuity guard', not because the cell uses it.
- src/cell.rs is 9,040 lines (45% of the crate) holding the entire per-pass cycle as one type with no internal module boundary; five functions carry #[allow(clippy::too_many_arguments)].
- No stub/TODO/unimplemented!/panic!-in-Result markers found anywhere in src/, and no #[ignore]d tests -- the crate itself is code-complete and hardened; the gap is deployment and wiring into a Cloud Run/execution-node target, not missing logic.

## edge-libs

Seven edge libraries (arbitrage, feature-dag, orderbook, protocols, routing, sequencing, strategy) are individually well-designed and heavily unit-tested, and their "hot path" pieces (arbitrage scan, cycle path routing, mirror/extension gating, reprice/rate-limit, book state, sequencer, strategy compiler/runtime) are all wired together correctly inside qip-edge's Cell and qip-edge-node's composition root. But qip-edge-node is never deployed (execution_nodes = {} in every Terraform environment), so that entire correctly-wired chain currently runs only under `cargo test`. Independently, roughly half of qip-routing (venue selection, order-type selection, health scoring, consolidation, the Gateway trait/SimulatedGateway/NativeGateway) and all of qip-protocols' actual wire decoders (FIX/ITCH/SBE) have zero production call sites anywhere, reached only by their own crate tests.

Notable gaps:

- qip-edge-node (the only composition root that wires qip-arbitrage, qip-feature-dag's FeatureEngine, qip-protocols' registry, qip-routing's path/mirror/reprice subsystems, qip-sequencing's Sequencer, and qip-strategy's live runtime together) is never deployed: execution_nodes = {} in infrastructure/environments/{dev,test,stage,prod}/terraform.tfvars.
- qip-edge-node's production StrategyInstaller compiles every strategy with an empty FeatureCatalogue::new() (strategies.rs:355), so any StrategySpec referencing Expr::Feature(key) is structurally refused at compile time on the live path -- confirmed by tracing the exact refusal in qip-strategy's compile.rs:437-441.
- qip-feature-dag's FeatureEngine is constructed in production (qip-edge-node/main.rs:360) but no code ever calls .register() on it, so it is permanently empty; the crate's own 12-feature standard_suite has no production caller anywhere.
- qip-routing's venue-selection subsystem (Router, HealthTracker, select_order_type, Consolidator) and its Gateway trait/SimulatedGateway/NativeGateway are entirely unreached; qip-edge-node built its own independent SimulatedGateway/NodeGateway on top of qip-brokers instead of reusing qip_routing::gateway.
- qip-protocols' actual venue-wire decoders (FIX, ITCH, SBE, JSON framing) are fully implemented and tested (51 tests) but never instantiated in production; the only decoder wired into a deployable binary is a local synthetic DepthDecoder reading from the simulated venue's own depth.

## frontend

The portal is a real, deployed Next.js console (Cloud Run/GitOps, dev, behind IAP) that reads qip-api through a self-hosted BFF gateway with a structural write-allowlist, real session/IAP auth, and 182 Playwright tests; landing is a fully-built, CI-tested but never-deployed marketing site whose own README documents that it word-for-word duplicates the portal's separate (marketing) route group; of the 11 shared frontend/packages/*, only auth, validation, brand and (indirectly, via a regex-parsed build script) design-tokens are actually consumed — the other seven (analytics, api-client, charts, feature-flags, shared-types, testing, ui) are wired into next.config.ts's transpilePackages and portal's package.json but have zero import sites anywhere in the tree, most being pure re-export shims pointing back into the portal's own source.

Notable gaps:

- landing has zero Terraform/GitOps/deploy.yml wiring despite a built Docker image and a pre-authorized Identity Platform hostname (environments/dev/terraform.tfvars:455,478-482) — CI-tested (ci.yml frontend-landing job, 13 Playwright tests) but reached_from_production is n/a.
- The portal's own (marketing) route group and frontend/landing independently hand-write the same eleven/twelve marketing pages; frontend/landing/README.md:44-52 calls this 'a holding position, not a design' and says the portal's copy should become redirects — not done.
- @algorik/api-client, @algorik/charts, @algorik/ui, @algorik/testing are 9-31 line files whose entire body is `export {...} from "../../../portal/src/..."`; @algorik/analytics and @algorik/feature-flags are fully-implemented (88 and 68 lines) but have zero callers anywhere; @algorik/shared-types (21 lines) already had one unused export set deleted and its two remaining types are also uncalled.
- @algorik/design-tokens is never imported by TypeScript at all — frontend/scripts/generate-theme-css.mjs instead regex-parses the package's source text at build time to emit portal globals.css, a parser the file's own comment says 'throws loudly' on a malformed match.
- portal's lib/sim (seeded/simWalk/simPick/simBetween) and the SimulatedBanner/SimChip components meant to display it per portal/CLAUDE.md's 'simulated data must be labelled' rule have zero call sites in any page — every current (portal) page reads real qip-api data instead.

## infrastructure

A 26-module Terraform root (`infrastructure/terraform`) wires GCP for a Cloud-Run-plus-one-execution-node architecture (ADR 0022/0024/0036), with 4 environment tfvars where only `dev` (project `algorik-dev`) has ever held a real project. Every safety-relevant gate (paper-trading ceiling, venue-credential readability, Binary Authorization, trust-zone default-deny) is applied and test-covered in dev, but the platform is not currently serving traffic: the GitOps control-plane cluster that reconciles Cloud Run services is suspended because Argo CD's upstream image fails the CRITICAL scan gate, and the console/portal image has never been built (TO-PIN in every environment).

Notable gaps:

- gitops-control-plane cluster in dev is applied-then-suspended: Argo CD v3.5.2 fails vendor.yml's CRITICAL Trivy gate on CVE-2025-68121 (unfixable upstream — vulnerable kustomize/git-lfs binaries are downloaded pre-built by every Argo CD release), and the platform's own remedy (argocd-patched.Dockerfile) has never been dispatched, so 0 Cloud Run services are actively reconciled today
- qip-portal is TO-PIN in every environment's gitops/envs/<env>/kustomization.yaml — deploy.yml has never built the console image, so the portal's RunService cannot come up regardless of the cluster
- execution_nodes = {} in all 4 environments: the ADR 0035 shadow-mode node in dev is fully specified in a tfvars comment but blocked on 2 human acts (boot-image bake never dispatched; region_allocation never chosen, deliberately never defaulted)
- modules/observability's 9 alert policies and the Cloud Run metrics-collector sidecar are both gated off: Google's own cloud-run-gmp-sidecar 1.9.2 was reviewed and REFUSED (CVE-2026-56854, no fixed tag published) so workload_metrics_exist stays false everywhere and nothing is scraped in production
- Kargo's promotion chain can only ever reach dev today — promoting to test/stage/prod would write dev's image digests into a registry that doesn't hold them and an attestor that never signed them (documented, unresolved architecture question in gitops/kargo/README.md)
- test/stage/prod environments have project_id = "unprovisioned" (a value the root's own validation refuses at plan time) — no GCP project has ever existed for 3 of the 4 environments
- modules/data, modules/ai, modules/connectivity, modules/scc, modules/public-edge, modules/dns-zone, modules/gitops-gateway, modules/iap-edge are all fully built and either test-covered or documented, but every enabling flag/hostname is off/empty in every committed tfvars, so they provision 0 resources anywhere

## kernel-cycle

qip-kernel's cycle.rs defines the eight-stage Stage/StageOutcome/CycleReport types (pure data, no I/O), and platform.rs's core (Platform::new and its three variants, run_cycle, the eight stage_* methods, ingest_cell_report, learn_from_cells, learn_from) is the actual loop: run_cycle calls all eight stages unconditionally in order, times each, charges cost, records telemetry, and journals the cycle to a DurableLogTransport-backed event log opened at assembly.

Notable gaps:

- run_cycle refuses (not journalled) a cycle dated before its own reasoned_through watermark, deliberately leaving no event-log trace of the refusal (platform.rs:9010-9012,9174-9209).
- A cycle journal write failure is recorded only as a LEARN-stage problem, not a cycle failure -- the process keeps trading if its own journal can't be written (platform.rs:9133-9148).
- stage_simulate's capacity probe swallows any refusal to None rather than surfacing it as a stage problem (platform.rs:12576-12581).
- learn_from_cells and learn_from have no direct backend/crates/apps/*/src caller; both are reached from production only transitively, via stage_learn's private sub-calls review_strategies and calibrate_resolved.
- platform.rs is 26,172 lines total; this record covers only the core-loop/ingest/learn surface named in the task, not the file's other subsystems (capital calls, capital fabric wallet/corridors, products, registrations, model promotion, etc.).

## libs-finance

Six dependency-light lib crates (~50,058 lines including tests) forming the platform's financial object model, market structure, numerics, accounting, risk-limit and governance layers. - qip-financial/src/physical.rs (1072 lines: PhysicalArbitrage, LandedCost, Customs, Spoilage, LogisticsTerms, 11 embedded tests) has zero callers anywhere in the workspace outside its own file -- internally hardened but unreachable from any other crate, production or test.
